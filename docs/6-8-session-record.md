# 6-8 会话记录：Prompt 压缩、字段扩展与回收策略

本文记录 6 月 8 日至今的连续改动，保留设计决策背景，避免后续遗忘。

## 一、Eval Prompt 压缩（6-8）

### 改动
`entity_eval/agent.py` 的 `SYSTEM_PROMPT` 从 ~89 行压缩到 ~43 行。

### 思路
原 prompt 存在大量重叠：
- "核心目标"≈"应输出的具体事件边界"的概括版
- "不应输出的边界"≈"禁止输出"的弱化版
- "中性判断""产品/品牌映射"各有独立段落

### 压缩后结构（4 块）
1. 任务定义
2. 必须输出
3. 明确不输出
4. JSON 输出格式 + 示例

### 效果验证
同 seed 444 random 100 对比：

| 指标 | 原版 | 压缩版 | 变化 |
|------|------|--------|------|
| wall_clock | 60.8s | 42.8s | -30% |
| prompt_tokens | 183,759 | 111,359 | -39% |
| completion_tokens | 12,879 | 8,900 | -31% |
| 原始实体数 | 180 | 132 | -27% |
| 后处理过滤 | 17 | 0 | 不需要了 |
| 合并后实体 | 163 | 131 | -20% |

有真正舆情实体的文章抽取量一致（22 篇大文章仍是 22），边缘文章（金价品牌、名单、纯交易数据）在 LLM 层面自过滤。

### 踩坑
`response_format={"type": "json_object"}` 要求 prompt 必须包含 `json` 关键词。把"输出格式"改为"JSON 输出格式"解决。

## 二、Review Sheet（6-8）

### 改动
`entity_eval/run.py` 新增 `_add_review_sheet()`，xlsx 输出包含两个 sheet：

| Sheet | 用途 | 特性 |
|-------|------|------|
| `entities` | 数据 | 无合并单元格，有 autofilter |
| `review` | 人工审查 | doc_id/headline/content 合并单元格，居中对齐，有 autofilter |

### 迭代过程
1. 初版：full content + wrap_text → content 撑大行高
2. 尝试：固定行高 + no_wrap → 用户不习惯
3. 终版：全文保留 + wrap_text + 居中对齐 + autofilter

## 三、风险类别字段 risk_type（6-8）

### 枚举值
| 类别 | 适用场景 |
|------|---------|
| 产品质量 | 产品召回、事故、质量问题、食品安全、不合格 |
| 财务风险 | 亏损、减值、债务违约、资金链断裂、业绩下滑 |
| 监管合规 | 处罚、诉讼、监管问询、立案、整改通知 |
| 经营风险 | 停产、裁员、关店、供应链中断、产能不足 |
| 竞争风险 | 份额下滑、被竞品超越、客户流失 |
| 品牌声誉 | 负面舆情、丑闻、公关危机 |

### 设计决策
- 仅在 entity_sentiment 为"利空"时填写，利好/中性留空
- 多选：同一事件涉及多个维度时填写多个
- 存储格式：逗号分隔字符串（如"产品质量，监管合规"），不用 JSON 列表
- 合并时做 set union

### 改动文件
- `agent.py`: `EntityEvalResult` 加 `risk_type: list[str]`，prompt 输出格式加字段，`_parse_response` 兼容处理
- `run.py`: `ENTITY_COLUMNS` 加 `risk_type`，entity dict 序列化，`_merge_entity_rows` 合并时 union，review sheet 加列

## 四、影响程度分级（6-8）

### 设计
- `impact_level` 仅在利空时填写
- 大：破产、并购、重大处罚、业绩暴雷、大规模停产、工厂事故
- 中：新产品发布、中标项目、常规诉讼、产线投产
- 小：边缘业务调整、小额投资、局部产品问题、轻微舆情

### 思考
不考虑 0-1 连续评分，因为 LLM 给绝对数值不可靠，不同 call 之间不可比。

## 六、行业报告规则前置（6-8）

### 背景
reren 诊断发现：行业报告/行业综述中有经营数据的公司（人形机器人、养殖业文章）被模型归为"行业背景"拒掉。

### 改动
1. 新增 `核心原则` 放在 task 定义之后、所有规则之前
2. 示例从"文心5.0 vs OpenAI"替换为"人形机器人行业报告"

### 效果
仅友邦保险 1 篇被捡回，人形机器人、养殖业等仍漏。实体总数从 122 降到 96（prompt 变长后模型趋于保守）。

## 七、Rerun / Retry 策略（6-8）

### Rerun（诊断模式）
`--rerun-empty`：0 实体文章用宽松 prompt 回抽，结果单独写 `rerun_entities.csv`，不合并。

宽松 prompt 与正式 prompt 的区别：去掉"仅被提及/名单/对比对象"等过滤，只保留硬排除项（个人、政府、媒体等）。

诊断目的：人工看宽松版抽到的东西，判断是"真漏了"还是"确实是噪音"。

### Retry（捡漏模式）
`--retry-empty`：0 实体文章用正式 prompt 重跑，成功则合并到最终结果。

注意 `--rerun-empty` 与 `--retry-empty` 互斥。

### 效果
retry 的恢复率很低（1/24），模型对 0 实体文章的判断稳定，同 prompt 再跑意义不大。

## 当前 prompt 版本（截至本次会话）

### Eval prompt 结构

```
任务定义
  ↓
核心原则（行业报告有数据的公司应输出）
  ↓
必须输出（4条）
  ↓
明确不输出（5条）
  ↓
JSON 输出格式
  ↓
影响程度分级（大/中/小，仅利空）
  ↓
风险类别说明（6类，仅利空，多选）
  ↓
示例（人形机器人行业报告）
  ↓
映射示例（3组产品→母公司）
```

### Judge prompt 结构

```
任务定义（precision-only）
  ↓
有效实体
  ↓
应判 extra
  ↓
JSON 输出格式 + 示例
```

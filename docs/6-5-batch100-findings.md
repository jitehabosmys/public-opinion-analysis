# Batch 100 实验记录：扩大样本后的结果与发现

本文记录 6 月 5 日在 `batch=100` 后的实验结果、从前 100 条到随机 100 条的稳定性观察，以及新增后处理和 precision-only judge 后的发现。

## 背景

在 `batch_30_eval_5 / batch_30_judge_5` 上，实体抽取已基本解决以下问题：

- 列表/案例类文章抽爆。
- 商品、币种、个人、政府机构等非目标实体混入。
- 同一 `doc_id + entity + entity_sentiment` 重复。
- judge 不理解 `mapped_from` 导致母公司被误判为 extra。

随后将样本量扩大到 100，并做两类实验：

1. `head(100)`：继续使用原始数据前 100 条。
2. `random(100)`：新增随机抽样能力，用不同 seed 测试稳定性。

## 代码侧改动

### 1. Eval 后处理过滤

在 `entity_eval/run.py` 中新增后处理过滤，执行顺序为：

```
LLM 原始输出 all_entities
    -> 后处理过滤
    -> 同向实体合并
    -> 写 entities.csv / entities.jsonl
```

当前过滤依据是 `sentiment_reason` 中模型自己已经承认“不应输出”的表述。

已有过滤 pattern：

- `仅提及`
- `仅作为`
- `仅被提及`
- `无具体事件或数据`
- `无具体事件或业务影响`
- `无具体协议或业务影响`
- `没有具体事件`
- `未提及具体`
- `未涉及其自身`
- `只是背景`
- `作为对比`
- `历史背景`

summary 中新增字段：

- `total_entities_before_filter`
- `post_filtered_entities`
- `post_filter_details`
- `total_entities_before_merge`
- `total_entities`

### 2. Judge 改为 precision-only

原先 judge 同时输出：

- `missed`
- `extra`

问题是 `missed` 经常脑补：

- 把名单/案例实体算作遗漏。
- 把泛泛客户关系算作遗漏。
- 把别名/子公司算作遗漏。
- 在板块综述中要求抽更多股票。

因此 judge 改成只检查 precision：

- 不再检查遗漏。
- 不再输出 missed。
- 只判断 extracted records 中哪些不应输出。

summary 中：

```json
"recall_evaluation_enabled": false,
"avg_entity_recall": null
```

### 3. Judge 输入包含完整实体记录

judge 不再只接收 entity 名称，而是接收：

```json
{
  "entity": "...",
  "mapped_from": "...",
  "entity_sentiment": "...",
  "sentiment_reason": "..."
}
```

这样可以避免 `mapped_from` 场景中，产品出现在原文、母公司出现在输出里时被误判为 extra。

### 4. 随机抽样能力

`entity_eval.run` 新增：

```bash
--sample-mode {head,random}
--seed SEED
```

默认仍为 `head`，兼容原有行为。

随机抽样示例：

```bash
uv run python -m entity_eval.run \
  -n 100 \
  --sample-mode random \
  --seed 111 \
  -w 4 \
  -o output/6-5/random_seed_111_batch_100_eval_1
```

## Head 100 结果

### batch_100_eval_1 / batch_100_judge_1

这是扩大到前 100 条后的第一版结果，judge 仍包含 recall。

| 指标 | 值 |
|------|----|
| eval 成功 | 100/100 |
| 实体数 | 164 |
| 有实体文章 | 80/100 |
| 重复同向实体 | 0 |
| judge recall | 0.853 |
| judge precision | 0.982 |

主要发现：

- 整体 precision 较高。
- recall 中仍有大量 judge 幻觉。
- 低 recall 样本混杂了真实漏抽和 judge 口径冲突。

典型 judge missed 口径冲突：

- 网站制作公司名单：judge 要求抽名单中的服务商。
- 德赛西威客户关系：judge 要求抽泛泛客户关系。
- 山东儒原案例：judge 要求抽帮扶/案例参与方。
- 板块行情文章：judge 要求抽更多受益股。

## 多 seed 稳定性

随后跑了 3 组随机 seed：

- `random_seed_111_batch_100_eval_1`
- `random_seed_222_batch_100_eval_1`
- `random_seed_333_batch_100_eval_1`

### 指标对比

| seed | 实体数 | 有实体文章 | 后处理过滤 | 重复同向实体 | judge precision | extra |
|------|--------|------------|------------|--------------|-----------------|-------|
| 111 | 130 | 74/100 | 1 | 0 | 0.984 | 5 |
| 222 | 108 | 74/100 | 3 | 0 | 0.995 | 1 |
| 333 | 108 | 74/100 | 3 | 0 | 1.000 | 0 |

### 稳定性观察

稳定点：

- 3 组都是 100/100 成功。
- 有实体文章均为 74/100。
- 重复同向实体均为 0。
- precision 均大于 0.98。
- 后处理过滤数量很少，不是靠大量硬过滤抬高 precision。

不同点：

- 实体数在 108 到 130 之间波动，主要由样本分布决定。
- seed=111 中市场/公司事件密度更高，因此实体数更多。
- seed=333 最干净，judge extra 为 0。

## 新增后处理建议

基于 batch_100 和多 seed 的 extra，建议继续补充以下 pattern：

- `对比对象`
- `无自身事件`
- `未提供具体事件`
- `无具体事件支撑`
- `无具体业务事件`

这些 pattern 比“只是座谈”“只是午宴”更泛化，不是对单一文章过拟合。

暂时不建议加入：

- `只是座谈`
- `只是午宴`

原因是这类表达过于具体，容易把 prompt/后处理绑到个别样本文风上。

## 当前结论

扩大到 100 条后，当前方案表现稳定。

可以确认的点：

- 抽多问题已明显缓解。
- precision 在随机样本上稳定高于 0.98。
- `mapped_from` 相关误判已基本解决。
- 同向重复合并稳定。
- 后处理过滤有效且数量较少，没有明显依赖硬规则刷分。

仍需注意的点：

- judge 已经是 precision-only，不再衡量 recall。
- 0 实体文章仍需人工抽查，确认是否存在系统性漏抽。
- 板块行情综述是否抽所有个股，需要业务口径决策。
- 个人名偶发输出仍可能存在，如 `杨生荣`。
- “对比对象/无自身事件/无具体业务事件”类后处理还可增强。

## 建议下一步

1. 补充更泛化的后处理 pattern：

```text
对比对象
无自身事件
未提供具体事件
无具体事件支撑
无具体业务事件
```

2. 对随机样本中的 0 实体文章做人工抽查。

建议每组 seed 抽 10 条 0 实体样本，看是否大量漏掉标题即事件的公司。

3. 明确板块行情综述口径。

可选方向：

- 宽口径：文章明确提到某公司涨停/大涨/大跌，就抽。
- 窄口径：只抽主因实体和文章重点展开实体，不抽所有联动股。

4. 暂时不再大改 prompt。

当前问题更适合通过后处理和业务口径决策解决，而不是继续堆 prompt。
